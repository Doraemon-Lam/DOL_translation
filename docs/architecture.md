# 架构与实验边界

## 运行路径

客户端 UTF-16 文本 → 原生字形生成函数 → 精确译文查找 → 原函数生成中文的尺寸及字形缓存。

此入口位于文字转换成缓存之前。直接修改先前找到的 UTF-16 临时缓冲区没有改变画面，因此没有继续沿用单次内存改字方案。早期 Frida 实验曾导致闪退，发行实现不包含 Frida。

客户端函数采用 x86 `thiscall`，替换入口使用 `fastcall` 接收 `ECX` 和占位 `EDX`，原样转交其他参数和返回指针。代码、主模块摘要、RVA 和前导字节被绑定为一组，不能独立更换其中一个来宣称兼容新版本。

## 词库

基础词库在安装钩子之前读取，SHA-256 必须与构建时生成的摘要相符。精确匹配补译优先于基础词库；最初四个基础验证标签在代码中也有固定映射。

格式为 `DOLTXT1\0`（8 字节）、小端 `uint32` 条目数，随后重复：小端源字符数、目标字符数、UTF-16LE 源文本、UTF-16LE 译文。字符数按 UTF-16 代码单元计算，不带终止 NUL。

补译文件最多 1 MiB / 10,000 条；单条最多 4096 个 UTF-16 代码单元。NUL 和当前入口不支持的脚本控制字符被拒绝，允许 CR/LF。

## 热更新

JSON 编译器先写 `.pending`，同步落盘，再原子替换正式文件。后台线程解析完整新文件后才原子发布映射。显示线程不读文件，也不等待在线翻译。

旧映射保持存活到游戏退出，避免其他线程仍持有译文指针时释放。每会话最多发布 32 版补译，达到上限后需重启。当前画面已经缓存的字形不会自动刷新，需要重新打开相应对话。

## 漏译记录

未知日文经固定长度队列转给后台线程写 UTF-8 JSONL。显示线程使用非阻塞入队；队列满或锁繁忙时允许丢弃。记录去重只在当次会话内生效，不自动上传，不自动翻译。

原始日志可能含玩家聊天和名字，永远不应作为发布资产直接打包。

## 验证范围

- 六项 Python 词库测试，包含 UTF-16 代理对、变体覆盖优先级、截断和控制字符。
- 自建 32 位宿主的 1000 次转接，参数、返回指针、未知文本透传及停用检查。
- 基础词库摘要、后台日志和两次真实文件热更新，旧译文指针仍有效。
- DLL 拒绝在非游戏宿主安装。
- 开发过程用户确认过部分选项和造船说明正文。完整剧情覆盖、所有排版、其他客户端版本和长期稳定性均未得到证明。

整理版与开发目录独立，不带个人进程号、原始内存地址、游戏二进制、第三方大词库或崩溃转储。
